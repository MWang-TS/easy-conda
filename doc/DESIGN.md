# Easy Conda：Windows 桌面环境管理器设计方案

## 1. 产品目标

面向不熟悉命令行的 Windows 用户，用一个 Tauri 桌面客户端发现、创建、维护和迁移 Conda 环境。所有会改变环境的操作都应可预览、可追踪、可取消（在底层允许时），失败时给出可执行的修复建议。

**产品原则**
- 环境与包是核心对象；常用动作一到两步可达，危险操作明确确认。
- 兼容用户已有的 Conda/Miniforge/Mamba 安装，不强迫迁移到应用自带运行时。
- 默认使用 Conda 原生求解器与配置语义，不在客户端重新实现依赖求解。
- 网络源、渠道优先级、代理与证书配置透明可见；不偷偷改用户全局配置。
- 导出格式忠实描述可重建内容；明确区分 Conda 包与 pip wheel。

## 2. 用户与关键场景

1. **首次使用**：自动发现电脑上的 Conda 安装；未安装时提供 Miniforge 安装引导，显示安装位置、许可信息与下载来源。
2. **浏览环境**：查看环境名称、路径、Python 版本、平台、包数、磁盘占用（可用时）、最近操作；搜索/筛选/排序。
3. **创建环境**：输入名称或路径，选择 Python 版本、渠道/镜像、依赖规格；显示求解计划和将下载的包，再确认执行。
4. **维护环境**：查看包、搜索包、安装/升级/移除；查看版本与来源；执行前展示变更摘要。
5. **复现与迁移**：从 YAML、requirements.txt、explicit spec 或离线包目录创建；导出环境定义、精确包清单或可搬运归档。
6. **排障**：查看命令输出、错误码、日志路径、渠道连通性与诊断报告；一键复制脱敏诊断信息。

## 3. 重要格式边界：wheel 不是 Conda 环境归档

Conda 包不等于 Python wheel。Conda 环境中可能包含 Python 包、非 Python 工具、编译器运行时、CUDA/MKL 等原生库及平台相关二进制。无法可靠地将任意 Conda 环境的所有依赖转换成 wheel。

产品应提供以下明确选项：

| 目标 | 推荐导出 | 说明 |
|---|---|---|
| 可读、跨平台重建 | `environment.yml` | 依赖规格为主；版本/平台可导致解析结果不同 |
| 同平台精确重建 | Conda explicit spec (`conda list --explicit`) | 精确到包 URL/build，适合相同 OS/架构；私有源 URL 需留意可达性 |
| 无网安装 Conda 依赖 | 离线包仓库/包缓存 + explicit spec | 保留 `.conda`/`.tar.bz2` 包及渠道元数据；验证包完整性，目标端使用本地 channel |
| 搬运整个环境 | `conda-pack` 归档（可选集成） | 适用于兼容平台；目标端解包后需执行修复前缀步骤；不是 wheel |
| 仅导出 pip 依赖 | `pip download` wheelhouse + requirements 文件 | 仅覆盖 pip 可获取的 wheel；源码包可能需构建工具；不覆盖 Conda 包 |

导出向导应按目标平台标记兼容性，显示预计体积、缺失包和许可/私有源风险。离线目标机无网络时，若需要 Conda 包，应将 Conda 包归档/本地 channel 一并交付，而不能只交 wheelhouse。

## 4. 信息架构与界面

### 主导航
- **环境**：环境列表与详情，是默认页面。
- **包**：当前选中环境的包管理。
- **任务**：下载、求解、安装、导出等长任务队列与历史。
- **源与设置**：Conda 安装、渠道、代理、缓存、诊断、更新。

### 环境列表页
左侧窄导航；中间环境表格；右侧详情面板。表格列：名称、Python、包数、路径、状态。顶部提供搜索、排序和“新建环境”；每行提供打开详情、终端打开、导出、克隆、删除等动作。删除需显示完整路径并二次确认。

### 环境详情
顶部显示名称、路径、Python/平台和状态；下方采用“包 / 历史 / 导出”分段视图。包表格支持名称、版本、来源、类型（Conda/pip）搜索筛选。安装/升级/移除统一进入变更预览，再执行。

### 新建环境向导
1. 命名与位置：名称、默认 envs 目录/自定义路径、冲突校验。
2. Python 与依赖：版本选择、按名称添加依赖、导入 YAML/requirements。
3. 下载源：沿用当前配置或选择预设/自定义渠道；展示渠道顺序与优先级。
4. 求解预览：计划增删改、下载大小（若可得）、警告；确认后提交任务。

### 视觉与交互
采用紧凑的桌面工作台布局，信息密度高但有清晰层级。危险操作使用明确文字确认；长任务显示分阶段进度、实时日志折叠区、取消按钮和完成/失败结果。所有关键操作支持键盘导航，窗口窄时详情面板切换为独立页面/抽屉。

## 5. 技术架构

### 客户端
- **Tauri 2** 桌面壳与 Web 前端；前端建议 TypeScript + React，组件与状态管理按团队现有技术栈选型。
- 页面只调用受控的 Rust command API，不拼接 shell 命令。
- 任务状态通过 Tauri event 推送；日志窗口可限量缓存并支持复制/保存。

### Rust 核心
建议拆分模块：
- `discovery`：定位 Conda/Mamba 可执行文件与根前缀，读取环境列表。
- `conda_cli`：统一命令构造、参数校验、进程启动、输出解析与错误归类。
- `environment`：环境详情、创建/克隆/删除、导入导出。
- `package`：包查询与变更计划执行。
- `channels`：读取/编辑应用管理的配置、连接测试、镜像预设。
- `jobs`：任务生命周期、并发限制、取消、日志与历史。
- `archive`：环境归档、离线 Conda channel、pip wheelhouse 生成与校验。
- `diagnostics`：版本/路径/配置/网络自检与脱敏报告。

所有外部进程以参数数组启动（`Command::new` + `args`），不得经由 `cmd.exe /c` 拼接用户输入。优先使用 Conda JSON 输出（如 `--json`）；解析失败时保存原始输出并提示兼容诊断，不依赖脆弱的英文文本解析。

### Conda 兼容策略
- 探测常见安装：Anaconda、Miniconda、Miniforge、Mambaforge、micromamba，以及 PATH 和已登记安装位置。
- 对每个可执行文件查询版本、根前缀、平台与环境；多个安装并存时允许用户选择默认实例。
- 通过能力探测而不是只按版本号分支；区分 `conda`、`mamba`、`micromamba` 的参数差异。
- 首版将 Conda CLI 作为执行后端，避免自行管理 Conda 协议和 solver；之后可评估 libmamba/专用 API，但须保留兼容回退。

### 状态与存储
- SQLite 保存任务历史、用户偏好、应用自管的渠道配置及最近选择；不缓存可从 Conda 重建的权威环境状态。
- 配置备份后再写入；默认只写应用专属配置文件或命令级参数，修改用户 `.condarc` 前明确告知并可回滚。
- 不保存认证令牌明文；优先使用 Windows Credential Manager/系统凭据存储；日志需遮蔽 URL 凭据、代理口令和令牌。

## 6. 安全、可靠性与生产要求

- Tauri capability 最小化，禁止不必要的 shell/plugin 权限；前端输入在 Rust 层再次验证。
- 对环境路径做规范化和边界校验，删除前检查目标确为环境且非 Conda base/root prefix；默认禁止删除 base。
- 子进程不以管理员权限运行；安装 Miniforge 时由用户明确启动并遵循官方安装许可。
- 环境变更采用单环境串行锁，避免并发安装/删除；读取操作可并行。
- 所有长操作异步执行，支持取消、应用退出时提示仍在运行任务；中断后提供恢复/诊断信息。
- 更新与安装包签名；Windows 发布考虑 MSIX 或签名 NSIS 安装器，提供卸载、版本回滚策略和自动更新开关。
- 崩溃报告默认关闭或明确征得同意；遥测可选、脱敏且可关闭。
- 目标用户数据与缓存提供清理入口；安装器不捆绑庞大的 Conda 全家桶，优先轻量客户端 + 按需引导安装/发现现有运行时。

## 7. 核心命令适配（示意）

具体参数须基于受支持的 Conda/Mamba 版本做能力探测与集成测试：
- 环境列表：`conda env list --json`
- 环境详情/包列表：`conda list -p <prefix> --json`
- 创建：`conda create -p <prefix> python=<version> ... --json`
- 删除：`conda env remove -p <prefix> --json`
- 环境导出：`conda env export -p <prefix>`；另提供 `--from-history` 作为更可移植的规格
- 精确清单：`conda list -p <prefix> --explicit`
- 环境变量/配置：通过对应 CLI JSON/配置命令读取；避免解析非结构化输出作为唯一来源

注意：命令参数、JSON schema、取消行为会随实现和版本变化，必须在 Windows CI 的真实 Conda 矩阵中验证。

## 8. 交付路线

### 阶段 1：可用 MVP
安装/发现 Conda；环境列表与详情；新建/删除环境；包列表；创建和包变更的任务日志；导入/导出 environment.yml；常见错误提示。

### 阶段 2：日常维护
包搜索与安装/升级/移除；求解计划预览；克隆环境；渠道/镜像配置与连通测试；任务历史、取消、诊断报告；多 Conda 实例管理。

### 阶段 3：离线迁移
精确 spec；同平台 Conda 离线包目录/本地 channel；pip wheelhouse；可选 conda-pack；兼容性与空间预估；归档完整性校验和清单。

### 阶段 4：企业与规模化
代理/私有源凭据、策略配置、离线安装器、组织级渠道预设、签名发布、自动更新、可审计操作历史；按真实用户反馈评估批量环境管理。

## 9. 测试与验收标准

- Windows 10/11 x64；至少覆盖 Conda、Miniforge、Mamba/micromamba 的受支持版本及无 Conda 环境。
- 有多个 Conda 安装、路径含空格/中文、环境名冲突、损坏配置、网络中断、镜像不可用、权限不足等场景。
- 创建、安装、删除结果与 CLI 对照一致；base 保护有效；取消不会误报成功。
- 导入/导出 YAML 往返测试；explicit spec 在兼容平台可复现；离线 channel 无网络安装测试；wheelhouse 明确只覆盖 pip 依赖。
- UI 自动化覆盖首次引导、创建、任务失败重试、删除确认和导出；Rust 层对路径校验、参数构造、脱敏与 JSON 解析做单元测试。
- 生产发布前验证代码签名、安装/升级/卸载、崩溃恢复、日志脱敏、无网络启动和可访问性。

## 10. 建议的首版范围

先交付 Windows x64、Tauri 2、Rust 后端 + TypeScript 前端，采用“发现现有 Conda，缺失时引导安装 Miniforge”的轻量模式。首版聚焦环境浏览、创建、包查看、YAML 导入导出与可靠任务日志；离线交付优先实现 explicit spec + Conda 包离线目录，再单独实现 pip wheelhouse。这样能让普通用户获得真正可用的离线重建能力，同时避免将 wheelhouse 误宣传为完整 Conda 环境包。
